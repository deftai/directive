## Amendment: the 0.99 forensic is wrong as causation

The 0.99 forensic is issue **#3282**, not a prior `docs/analysis` file.

#3282 recorded a real symptom: in two 0.99.0 consumer-container runs, 44–47% of agent turns went to making `directive check` pass (`verify:branch` with no diagnostic; missing `task` binary; `toolchain:check-consumer` wanted pnpm + a built CLI dist / self-build). After check went green it caught **zero** product defects. Product verification was squeezed into the last 1–2 turns.

#3282 then treated that turn sink as the cause of the two hard-task fails, and named `#3225` as a “likely multiplier” that “made previously-advisory failures mandatory.”

**Disconfirmed as cause.** #3282 shipped in 0.101 (toolchain preflight, named-cause failures, degraded skip, opt-in run-summary). 0.101 telemetry shows **2–8 gate invocations per trial** (about an order of magnitude down) and lower mean turns/cost. **Both tasks still fail.** A turn tax that you cut by 10× without recovering the tasks is not the mechanism that made them fail.

The 2026-08-13 transcript read is the better shape: product verify happened **mid-run**. The defect is the **gap after that verify**, plus an **end-of-run re-verify** that overwrote the earlier pass. #3282 described the contents of that gap (check / toolchain archaeology). It did not name what **inserted** the gap between 0.92 and 0.99.

This file is the amendment of record. A comment on #3282 points here. Do not treat “the done-gate turn sink caused these two failures” as current.

## What #3225 actually is (leading suspect, falsified as inserter)

#3225 (commit `fd7174b8`, 2026-08-09, ships in v0.99.0) teaches `pr:merge-ready` / `pr:watch` / the shared Greptile detector to treat should-not-merge / not-safe-to-merge **reviewer prose** as a hard merge-ready block.

It does **not** change consumer `task check`. It does **not** run unless those PR verbs run. The task A transcript is lifecycle + toolchain + self-build, not a reviewer-verdict fight.

#3282’s “#3225 made previously-advisory **check** failures mandatory” is a category error. #3225 is a **review-verdict** gate, not a check-composition change.

#3225 remains a **merge-path multiplier** if a run actually opens a PR and waits on review-cycle. It is not what inserted the verify-to-ship gap on this no-PR / pre-PR profile.

## Named cause (mechanism)

Three 0.92→0.99 changes compose. Together they put ~25 turns of process between a mid-run product pass and ship, then force a second verification.

### 1. Inserter: default envelope is merge-ready (#3153)

#3032 (already in v0.92.0) said: when the **intent** is through-merge, dispatch a merge-ready worker.

#3153 (commit `e2dddfd7`, 2026-08-06, in the 0.92→0.99 window) put this in always-on consumer `agents-entry`:

> Default story / through-merge unit of work is `drive-to: merge-ready`.

After a mid-run product pass, the agent is now instructed to keep going: xBRIEF lifecycle, pre-pr, `task check`, review-cycle, merge / `scope:complete`. That **is** the verify-to-ship gap.

At 0.92 the same hard task could verify output and stop. At 0.99 the always-on pin tells the agent the unit is not done until merge-ready ceremony finishes.

### 2. Amplifier: ceremony dial + deposit-as-project (#3214)

#3214 ships in v0.99.0 (`e08b4919`). Matrix:

- explicit `non-project` → **minimal**
- `L × mid × project` → **elevated** (already locked in `ceremony-dial.test.ts`)

`detectCeremonyProjectShape` returns `project` when any of these exist:

- `xbrief/PROJECT-DEFINITION.xbrief.json`
- `AGENTS.md` + `xbrief/`
- `.deft/core/`

A vanilla `directive init` consumer has all three. The **task** can be a one-shot hard engineering problem; the **deposit** still classifies as `project`. Explicit `non-project` is CLI/env only. So the “two hard non-project tasks” in the issue body never receive `minimal` unless the harness sets `DEFT_CEREMONY_PROJECT_SHAPE=non-project`.

On this profile (mid-tier + hard / L + deposit-as-project) the dial selects **elevated** once size and tier are known. Cold start with incomplete size was still `rapid` at 0.99; agents then escalate on evidence (skill + matrix). Elevated ceremony does **not** lighten mutation readiness or `task check` (#3156 / #3214 contract: rapid/minimal lighten informational cold path only).

This session reproduced the classifier: `projectShape=project from deposit layout` on a worktree that is not a one-shot scratch task.

### 3. Lengthener inside the tail: consumer check grew (#3145)

v0.92.0 `CONSUMER_CHECK_GATES`:

`doctor`, `toolchain:check-consumer`, `verify:branch`, `verify:cache-fresh`, `verify:wip-cap`, `verify:orphan-active`, `vbrief:validate`, `verify-strategy-output`

v0.99.0 added the #3145 trio (`6cc5f647`, 2026-08-06) and reordered cheap gates first (#3188):

`verify:test-boundary`, `verify:scope-provenance`, `verify:consumer-check-contract`

Defaults for test-boundary are **warn** until authored policy. Agents still run them. `#3156` (also 0.99) forbids clearing red by editing the gate. `toolchain:check-consumer` and `verify:branch` already existed at 0.92; they become expensive **because they now sit in a mandatory post-product merge-ready tail**, not because they were new.

Self-build (`toolchain:check-consumer` wanting CLI dist / treating a deposit as buildable source) is the #3282-class fight. It is not newly invented in 0.92→0.99; #3324 tracks the current deposit-as-source face. It **fills** the gap. It did not **insert** it.

### 4. End-of-run re-verification

Build / pre-pr / product-first done-gate skills require a check (or later `verify:ac`) before ship. After ~25 turns of unrelated work, the mid-run product pass is stale, so the agent re-runs. That is the window where the official comparison can contradict the earlier pass and the agent repairs the **oracle** (#3322) instead of the product.

#3284 / #3267 / #3285 (0.100–0.101) did not recover these tasks: either they did not fire (no stated AC / `none_stated`), or the end-of-run re-verify still overwrote the banked pass.

## Ruled out

| Theory | Why not |
|---|---|
| Budget exhaustion | Operator: both fails finished at ~1/3 max turns |
| Done-gate turn sink as **cause** | 0.101 cut invocations ~10×; tasks still fail |
| `#3225` as **inserter** | Detector is PR merge-ready only; transcript is lifecycle+toolchain |
| Ceremony dial as **sole** cause | Dial does not skip check; without #3153 there is no merge-ready tail |
| `#3145` as **sole** cause | Warn-default; same check without a post-product tail would not create a 25-turn gap after a mid-run pass |
| Self-build as **inserter** | `toolchain:check-consumer` already on 0.92 consumer check |
| `#3284` / `#3267` not firing as the 0.92→0.99 cause | Those shipped **after** 0.99; they failed to **recover**, they did not **introduce** |

## Intentional vs defect

#3153, #3214, #3145, #3225, and #3156 are intentional for **story / through-merge** work. They must not be relaxed to make two benchmark tasks green (#3156).

The defect is **over-application** to one-shot hard engineering tasks in a vanilla consumer deposit: default merge-ready + deposit classified as project + end-of-run re-verify after a mid-run product pass.
