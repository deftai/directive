## In plain English
Problem: on a reused cut, release Step 5 runs a short host smoke check (`pnpm run build`, then a few vitest files) through `spawnSync` with a timeout. When the time runs out, Node kills only the direct child, and the build and vitest processes under it keep running after Step 5 has failed.

What the critics found: the sync wrapper `runTimedChild`, which Step 5 already uses for its hygiene gates, is the right tool, but its result must tell the truth. Only the worker that holds the live child handle may kill; the calling thread cannot prove a numeric PID is still the smoke command. The last audit added two points: a worker stall left as a limit on the lean does not relieve the pain, and an empty survivor list proves nothing when the descendant scan failed or ran out of time.

Solution this lean proposes: `runSmokeCommand` runs each command through `runTimedChild` with the same safe spawn plan, environment and shared deadline. At the deadline the worker snapshots the tree, kills it and kills any survivor, as today, and now reports the outcome. It reports `stopped` only when the scan of the tree completed and no process is left; `survivors` with their PIDs when a known process is still alive; and `unverified` when the scan failed or ran out of time and no survivor is known. The calling thread never kills. A backstop expiry or a worker failure before the result gives `unverified` and names the PID the worker reported at spawn. Cleanup after such a worker stall is split to #6943 by the operator.

What this adds: one result field on the shared timed-child runner, a completeness flag on the descendant scan, one spawn message from the worker, a loop that reads every message on the port, and a start line per smoke command. No new constant and no new gate.

What it does not do:
- It does not clean up after a worker that stalls or fails before it reports. That case is reported as `unverified` with no kill, and its cleanup is #6943 (operator split, comment 7070629610).
- It does not change how the tree is listed. On win32 the listing uses `wmic`, which is missing on current Windows 11 builds (it is missing on the release host checked by the parent). There the scan fails, so a timed-out smoke command reports `unverified`, while `taskkill /T` still kills the tree.
- It does not stream smoke output live. Output is written when each command ends, and only the last 256 KiB of each stream is kept.
- It does not add a test that needs a built `dist` worker.
If confirmed, the synthesis would assert this design. The leftover next-build is #6943.

## Bound remedy
1. Smoke runner. `runSmokeCommand` (`packages/core/src/release/ci-reuse.ts`) runs its command through `runTimedChild` instead of `spawnSync`, with the plan from `smokeSpawnPlan` (command, args, `windowsVerbatimArguments`, cwd), `env: sanitizeTsLaneEnv(process.env)`, `timeoutMs` equal to the time left on the shared deadline, and the current platform. It takes the timed runner as an optional seam. `runHostSmokeCheck`, its `runner` seam and its single `RELEASE_CHECK_TIMEOUT_MS` deadline do not change. No new constant.
2. Scan completeness. The descendant scan reports whether it completed. A sibling of `listDescendantPids` returns `{ pids, complete }`; `listDescendantPids` keeps returning only the list for its other callers. `complete` is false when the scan budget runs out before the walk ends, or when any listing call fails: a spawn error (for example a missing `wmic` or `pgrep`), a timeout, or an exit status other than success or the command's no-match status (`pgrep` exit 1). The injected `listDirect` seam may return `null` to mean a failed listing. `killTreeAndProveEmpty` returns `{ remaining, scanComplete }`; callers that read only `remaining` do not change.
3. Cleanup outcome. `SupervisedGateResult` gains an optional field `treeCleanup` with the values `stopped`, `survivors` and `unverified`, an optional `survivorPids` list and an optional `lastReportedPid`. In `superviseTimedChild`, the deadline timer keeps the result of `killTreeAndProveEmpty`: a non-empty `remaining` gives `survivors` with those PIDs; an empty `remaining` with `scanComplete` gives `stopped`; an empty `remaining` without `scanComplete` gives `unverified`. When the deadline fires after the child has already exited (`confirmChildHandleForKill` returns null), or the plan's `killTree` test seam is used, the result is `unverified`. A result without a timeout has no `treeCleanup` field.
4. Only the worker kills. The kill at the deadline stays in the worker, which holds the live child handle, as today. `superviseTimedChild` takes an optional `onSpawn(pid)` callback. In timed mode the worker uses it to post `{ kind: "spawned", pid }` on the port as soon as the child starts, and posts its final result as `{ kind: "result", result }` before it notifies, as today. Suite mode keeps its untagged message. `runTimedChild` reads every queued message with `receiveMessageOnPort`, takes the `result` message as the result and remembers the last `spawned` PID. When `plan.timeoutMs` is set and the backstop wait expires, or the worker fails or ends with no `result` message, `runTimedChild` returns a failure with `treeCleanup: unverified` and `lastReportedPid` set to the remembered PID, if any. The calling thread never kills a process and never passes `lastReportedPid` to a kill function. The backstop of `timeoutMs + 15_000` and the worker termination on return do not change.
5. Result mapping in the smoke check. A timed-out result with `treeCleanup: stopped` returns `status: null` and an error that says the command passed the deadline and its process tree was stopped. With `survivors`, the error names the surviving PIDs and does not say the tree was stopped. With `unverified`, the error says the cleanup could not be checked and the command's processes may still be running; when `lastReportedPid` is set it names that PID and says it may already have exited and been reused. A spawn error or a missing worker returns `status: null` and that error. Step 5 fails in all of these cases, as today. Otherwise `status` is the exit code.
6. Output. Before each command the smoke check prints one line naming the command and the time left. The captured stdout and stderr are written to the release output when the command ends. The doc comment of `runSmokeCommand` states that output is delayed and keeps only the last 256 KiB of each stream.
7. Shared users. The Step 5 hygiene gates (`cached-orchestrator.ts`) get the same `treeCleanup` field and message handling through `runTimedChild`; they do not change how they read the result.
8. Tests. None needs a built `dist` worker.
   (a) Through the seam, `runSmokeCommand` passes the smoke plan, environment and time left, and maps each `treeCleanup` value (with and without `lastReportedPid`) and a spawn error as in item 5.
   (b) An in-process `superviseTimedChild` run of a smoke plan whose command starts a child that outlives the deadline and records its PID shows, after it returns, that the recorded PID is not running, on win32 and POSIX, and that the result is `stopped` when the scan completed and `unverified` when it did not.
   (c) With a fake `isPidAlive` seam that leaves a PID alive, `superviseTimedChild` returns `survivors` with that PID. When the child has already exited as the deadline fires, it returns `unverified` and no kill is attempted.
   (d) Scan completeness, in-process with the `listDirect` seam: a listing that returns `null` (failed) gives `complete: false`; a budget that expires before the walk ends gives `complete: false`; a full walk gives `complete: true`. With those seams, `killTreeAndProveEmpty` and `superviseTimedChild` give `unverified` for a failed listing and for an expired budget when no PID is left alive, and `survivors` when a known PID is still alive. The existing budget test keeps its list result and also asserts `complete: false`.
   (e) The message handling of `runTimedChild` is factored into one function that takes the receiving port and the wait outcome. It is driven through a real in-process `MessageChannel` with these sequences: spawned then result gives that result; result alone gives that result; spawned alone with a backstop expiry gives `unverified` with that PID; two spawned messages and no result give `unverified` with the last PID; no message after a worker failure gives `unverified` with no PID. The function has no kill seam.
   (f) The metacharacter-cwd test keeps a real execution, through the in-process runner with the plan `runSmokeCommand` builds, and asserts that `runSmokeCommand` forwards that plan.

## Acceptance Criteria
- Given a smoke command whose child outlives the deadline, when the smoke check times out, then after it returns the recorded child PID is not running, on win32 and POSIX.
- Given that case with a completed descendant scan and no process left, then the result carries `treeCleanup: stopped` and the failure says the process tree was stopped.
- Given a timed-out command where a known process survives the kill passes, then the result carries `treeCleanup: survivors` with that PID and the smoke failure names it, without saying the tree was stopped.
- Given a descendant listing that fails (for example a missing `wmic` or `pgrep`) or a scan budget that expires, with no known survivor, then the result carries `treeCleanup: unverified`, never `stopped`.
- Given the backstop of `runTimedChild` expires, or the worker fails or ends without a result, then the calling thread kills no process, the result carries `treeCleanup: unverified`, and the smoke failure names the PID the worker reported at spawn, if any.
- Given the child has already exited when the deadline fires, then nothing is killed and the result carries `treeCleanup: unverified`.
- `runTimedChild` takes the worker result from the `result` message even when a `spawned` message came first.
- The smoke check keeps one shared deadline of `RELEASE_CHECK_TIMEOUT_MS` for both commands, and no new timeout constant is added.
- The smoke spawn keeps `shell: false` and the project root only as the cwd; a real run in a directory named with shell metacharacters runs no extra command.
- Each smoke command prints a start line, and its captured output is written when it ends.

## Reject
- A test that needs a built `dist` worker (comment 7052343840, finding 3: no test in the suite depends on `dist` today; the message handling, scan and cleanup are tested in-process instead).
- A new logging or tee for smoke output (comment 7052343840, finding 4).
- A kill from the calling thread after a backstop expiry or worker failure (comment 7052396207, findings 1 and 2: a missing exit message does not prove the PID is still the smoke command, and a root exit does not cover the descendants).
