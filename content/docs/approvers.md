# Signed approvers (`approvers:enroll`)

Refs: #6945 · Related: [observable-scope.md](./observable-scope.md), [intent-constraint.md](./intent-constraint.md), [scope-provenance.md](./scope-provenance.md) (#5862 reserved)

A repository opts in by committing `.deft/approvers.json`. That file is the trust root for observable-scope and intent-constraint records. Its first version is a hardware key whose packed attestation verifies against vendor roots shipped with Directive. `none` and self attestation are refused. Later versions are signed by a key of the immediately preceding version, or they are a re-root by a newly attested key that no earlier version enrolled. Verify walks every first-parent version. Deleting the file, rolling it back, a second transition from one predecessor, or a shallow clone refuses. There is no level off: once the file has appeared, the repository stays signed.

`approvers:enroll --name <n>` roots when the file is absent (`--origin` is the https origin of the ceremony page) and otherwise adds a key. `approvers:enroll --name <n> --re-root` is the lost-all-keys path. `approvers:remove --credential <id>` drops one key. With no `--assertion` each verb prints a link and writes nothing. `--assertion` accepts only the page's trust file (`deft.approvers.v1` with `body` and `proof`). Another enroll or remove waits until that file is in git history. There is no terminal step.

The page is `content/tools/approvers/ceremony.html`. It shows the set as text, computes an approval challenge from the bytes it shows, and passes enrolled credential ids so a non-discoverable key can be selected. A root or re-root registration is bound to `deft.registration-challenge.v1`, and the assertion signs the transition payload. It adds a key only in the same session as an enrolled key's signature. One ceremony runs at a time. Deploy it at the origin named in the trust file with credentials the agent does not hold. Do not serve it from localhost.

At the signed level, `scope:record-observable-scope` and `scope:record-intent-constraint` take `--request` (writes nothing) and `--assertion <blob>`. A record is approved only when its approval verifies against an enrolled key over a payload rebuilt from this repository and the record's own fields. A hand-written record, a TTY mint, or a record merged under `DEFT_ALLOW_BOT_MERGE`, `policy:allow-bot-merge`, or a plain `gh pr merge`, without that approval, is not approved. Changing plan id, brief path, record path, `changeKind`, or the contract needs a fresh approval. An approval from another repository does not verify. One stale record does not fail an unrelated plan.

Without `.deft/approvers.json`, those two verbs keep the declared write (`kind: "declared"`). A declared record is not consent.

A valid approval proves a user-verified gesture by an enrolled authenticator over exactly this set. The human read the set only if the page ran on a device the agent does not drive and was deployed with credentials the agent does not hold. Windows Hello, Touch ID, a desktop USB key, and the desktop browser's cross-device QR are a lower review assurance than the phone's own browser. Residuals: removing the surfaces policy, editing CI, or pinning an older runtime turns the check off without forging an approval (#6207). An approval stays valid while its key stays enrolled, so deleting a record does not revoke it, and nothing expires. `plan.policy.onePrScopeProof` `signed` stays reserved (#5862). #6284 may reuse this trust root later.
